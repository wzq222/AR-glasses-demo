# 中车眼镜移动端检测模型公平对照设计

## 目标

在同一台华为 P20 Pro（CLT-AL00）上，对现有全图检测模型的不同移动端运行时和两类轻量检测器做可复现对照，选出兼顾全图召回、热态延迟、持续运行稳定性与商业许可的移动端方案。

本轮只评估“在全图中找出需要检查的带防松标记检查点”。防松线是否错位属于后续 ROI 状态模型，不得用候选检测成绩代替松动状态能力。

## 已知基线

- 当前 APK 使用 YOLOv8s-P2、640×640、FP32 ONNX，通过 ONNX Runtime Android CPU 四线程执行。
- P20 Pro 实测端到端 P50/P95 约 1926/1951 ms；持续满载热降频后可恶化到 3.6–5 s。
- 当前模型保留 stride-4/P2 小目标层，速度代价明显，但它是现有全图召回基线。
- 当前松动状态 MobileNetV3-Small ROI 模型未通过质量门，不参与本轮 APK 准入。

## 对照组

### A. 同权重、不同运行时

先保持模型结构、输入尺寸和权重不变，只替换运行时，以分离“模型太重”和“运行时不适配”两个原因。

1. `ORT-FP32-CPU`：当前 APK，作为不可变基线。
2. `NCNN-FP16-CPU`：当前 YOLOv8s-P2 转为 ncnn FP16，ARM CPU 四线程。
3. `NCNN-FP16-Vulkan`：与上一组相同模型，启用 Vulkan；如果算子回落或热态更慢，保留失败证据并停止该后端。
4. `MNN-FP32-CPU` 与 `MNN-INT8-CPU`：验证 MNN ARM 后端和量化收益。
5. `MNN-FP16-OpenCL`：验证 Mali-G72 GPU 路径；结果错误、频繁回落或热态退化即淘汰。
6. `MNN-HiAI`：尝试调用麒麟 970 NPU。模型转换、DDK、设备固件或算子兼容任一不满足时，记为“不支持”，不以 CPU 回落数据冒充 NPU 数据。

同权重运行时组必须先做逐张输出等价检查。FP32/FP16 的框坐标、类别和置信度允许数值微差，但匹配后不得出现超过既定容差的候选丢失；INT8 必须重新跑完整准确率门。

### B. NanoDet-Plus 轻量挑战者

- 首个配置为 NanoDet-Plus-m-1.5x、416×416。
- 使用与基线相同的真实训练划分、负样本和 hard-negative 清单，不打开 sealed-test。
- 先验证官方 stride 结构的速度与部署链；若 tiny/边缘目标召回未过门，再增加 stride-4/P2 输出，并单独记录额外算力。
- Android 首选 ncnn FP16；只有 FP16 通过准确率门后才制作 INT8 校准模型。
- 不使用未审计伪标签扩大训练集，不让生成图进入真实验证集。

### C. PicoDet 轻量挑战者

- 首个配置为 PicoDet-S/LCNet、416×416。
- 数据、增强、负样本、epoch 预算和验证划分与 NanoDet 组保持可比。
- 先验证标准模型；若 tiny 目标召回不足，再加入 stride-4/P2 特征层并单独评估。
- Android 同时保留 Paddle Lite 与 ncnn 两条可导出路径；以实机热态成绩决定运行时，不依据桌面 benchmark 选择。
- INT8 仅在量化校准集与真实训练图场景隔离、且量化后召回通过时准入。

### D. 参考但不首轮投入的模型

RTMDet-tiny、YOLO26n/YOLO11n 和其他更大模型只保留为后续参考。本轮不扩大候选集合，原因分别是移动端实机证据不足、全图小目标仍需自定义 P2，以及 Ultralytics 商业许可约束未解决。

## 数据与隔离

- 训练和开发验证只使用 Git 外的中车眼镜数据资产；现场原图、权重和生成资产不提交 Git。
- 使用现有冻结 train/val 场景划分；禁止按图片随机重分导致同场景泄漏。
- 带标记检查点集合用于主门；现有高准确率全图 fastener 验证集用于辅助检查“轻量化是否吞掉小目标”。
- sealed-test 在开发门全部满足前保持封存；任何调参、量化校准或阈值选择均不得读取 sealed-test。
- formal truth 不修改，其 SHA-256 必须保持 `B659FC8160BD7C49491BA4C560E1AF047CA837E54EE93E79826FEBAABCB0F001`。

## 统一推理契约

所有运行时通过同一个 Android 接口接收已经完成方向校正的 RGB Bitmap，并返回：

- 原图宽高；
- 候选框、类别、置信度；
- preprocess、inference、postprocess 和 total 延迟；
- 运行时、后端、线程数、精度、模型 SHA-256；
- 是否发生算子回落、初始化失败或内存错误。

模型实例在应用级只初始化一次。基准期间使用单推理队列和 `KEEP_ONLY_LATEST` 背压，不允许并发堆积帧制造虚假吞吐。

## 公平基准方法

### 准确率

1. 在桌面端先验证导出前后输出和 COCO 指标。
2. 将同一组验证图片复制到手机应用私有目录。
3. 每个后端按同一文件顺序、同一阈值和同一 NMS 参数运行。
4. 导出 JSONL，由现有评估器计算 precision、recall、AP50、每场景完整召回率以及 tiny/blur/lookalike 等误差桶。

### 性能

1. 冷启动记录模型初始化和首次推理，但不混入稳态延迟。
2. 预热五次后运行至少三十次静态图片推理，报告 P50/P95。
3. 连续相机运行十分钟，按每分钟记录 total P50/P95、结果更新率、PSS、CPU 温度与降频迹象。
4. 同一手机、同一电量区间、关闭充电、相同屏幕亮度和环境下完成所有后端。
5. CPU、Vulkan、OpenCL 和 HiAI 必须分别标识；回落到 CPU 时结果归入回落记录，不归入声明的加速后端。

## 准入门

### 第一轮生存门

- 主验证集 recall 不低于当前 YOLOv8s-P2 基线减 0.01。
- precision 不低于 0.60；低置信候选允许交给后续 ROI 复核，但不得形成无界误报。
- 完整场景召回率不得低于当前基线。
- 无场景泄漏、非法框、模型输出漂移或量化灾难。

### 移动端性能门

- 十分钟热态端到端 P95 小于 500 ms。
- 十分钟结果更新率不低于 2 FPS。
- PSS 不高于 250 MB，且无 OOM、ANR 或持续堆积帧。

### 最终选择顺序

1. recall；
2. 完整场景召回率；
3. 热态 P95；
4. precision；
5. PSS 与包体；
6. 许可证与维护成本。

速度达标但召回下降的模型不得胜出。开发验证达到高召回只代表可打开 sealed-test，不代表生产准确率；生产交付仍需真实现场独立测试和松动状态闭环。

## Android 接入边界

- 基准运行时通过独立适配器接入，不把 ncnn、MNN 或 Paddle Lite 逻辑写进 Activity。
- 手机相机实时页与眼镜照片导入共用同一推理接口。
- 眼镜照片通过 `MSG_FILE_RECV_FINISH` 保存完成后进入独立推理队列；不得占用 BLE/Wi-Fi 下载线程。
- 只有胜出模型进入默认 APK。其他运行时、模型和 benchmark 页面留在实验构建变体，不增加交付包体。
- 防松线状态继续输出四态契约：`ALIGNED / DISPLACED / DAMAGED_MARK / INSUFFICIENT`；本轮检测器只提供 ROI，不得直接输出松动结论。

## 失败处理

- 转换失败：保存转换器版本、算子名和最小复现，不手改权重绕过数值校验。
- 后端回落：明确记录实际后端；全图 CPU 回落不算 Vulkan/OpenCL/HiAI 成绩。
- 量化掉点：淘汰 INT8，保留 FP16 候选。
- tiny 召回不足：只为该模型增加 P2/stride-4 变体，重新计算 FLOPs 和热态指标。
- 热降频：以十分钟最差稳定区间为正式性能，不引用冷机峰值。
- 所有挑战者均失败：保留当前模型用于拍照后推理，实时画面采用低频检测加非模型跟踪，不虚报实时检测已经解决。

## 验证产物

- 每个候选的训练配置、依赖锁定和权重 SHA-256；
- 导出前后数值一致性报告；
- 开发验证指标与错误包；
- 手机逐次 JSONL、十分钟热态摘要和设备信息；
- 一张统一比较表和明确的胜出/淘汰理由；
- APK 构建、单元测试和目标手机安装冒烟证据；
- formal truth 前后哈希记录。

## 非目标

- 本轮不宣称解决防松线松动状态。
- 不把公开 COCO benchmark 当作本项目现场精度。
- 不因网上模型更新而跳过同数据、同设备复测。
- 不修改 formal truth，不打开 sealed-test 来调参，不把现场原图或模型权重提交 Git。
